## 现状定位（导致 5 分钟的主要原因）
- 当笔记长度 \> 8000 字符时，后端会先走一次“笔记压缩”（一次 DeepSeek 请求），压缩完再走“出题”（第二次 DeepSeek 请求）。两次串行叠加很容易到几分钟。见 [/api/start_stream](file:///c:/Users/sd676/Desktop/85%25%E4%B9%A0%E9%A2%98%E8%AE%AD%E7%BB%83/server.js#L2053-L2178)、[compressNotesToBoundary](file:///c:/Users/sd676/Desktop/85%25%E4%B9%A0%E9%A2%98%E8%AE%AD%E7%BB%83/server.js#L1845-L1870)。
- “压缩”这一步把整段笔记原文发给模型，且没有 `max_tokens`/输出长度硬限制；笔记越长越慢。
- 出题默认 `max_tokens: 1600` 且 prompt 要求“详细解析”，输出长、生成慢。见 [chatTextStream](file:///c:/Users/sd676/Desktop/85%25%E4%B9%A0%E9%A2%98%E8%AE%AD%E7%BB%83/server.js#L886-L911)、[makePackPrompt](file:///c:/Users/sd676/Desktop/85%25%E4%B9%A0%E9%A2%98%E8%AE%AD%E7%BB%83/server.js#L571-L599)。
- 主链路缺少显式超时/中断控制，网络抖动/服务端慢时会“无限等”。见 [chatJson](file:///c:/Users/sd676/Desktop/85%25%E4%B9%A0%E9%A2%98%E8%AE%AD%E7%BB%83/server.js#L803-L884)。

## 优化目标
- 10k 字符笔记：通常 \< 60 秒返回。
- 超长笔记：能在 90 秒内给出结果或明确超时退出（并自动降级），避免卡 5 分钟。

## 实施方案（只改后端 server.js；前端不动/最小化）
### 1) 降低“压缩笔记”触发率与成本
- 把压缩阈值从 `8000` 提升到更合理值（例如 `20000` 或按行数/段落数判断）。
- 压缩前对输入做截断（新增/复用截断函数），避免把几十 KB 原文直接丢给模型。
- 压缩请求增加硬限制：
  - 设置 `max_tokens`（例如 600~800）
  - 在提示词中要求“≤120 行/≤4000 字符”，并且只输出纯文本

### 2) 限制出题输出长度（更快生成 5~6 题）
- 将出题 `max_tokens` 从 1600 下调到 800~1000。
- 调整 `makePackPrompt()`：把“详细解析”改为“精炼解析（2~4 句/≤80 字）”，并要求不要生成冗长 meta。

### 3) 加超时 + 控制重试（防止耗时被拉长）
- 在 `getClient()` 给 OpenAI SDK 增加默认 `timeout`（如 60~90s）与 `maxRetries`（建议 0~1，避免默认重试把整体拖到几分钟）。
- 在关键调用点增加降级策略：
  - 压缩超时/失败：直接跳过压缩，用截断后的原笔记继续出题。
  - 出题超时/失败：降低题量到 3 道 + 更短解析，最多再试一次。

### 4) 增加 hash 缓存（重复生成秒回）
- 以 `hash(notesBound + MODEL + promptVersion)` 作为 key 缓存 pack：
  - 同一份笔记/同一套 prompt 再点开始，直接复用。
  - 缓存可放内存 Map（即可见效），后续可选持久化到文件。
